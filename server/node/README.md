# Tidesight collector for Node.js

The ingest endpoints of [`docs/protocol.md`](../../docs/protocol.md) (`/collect`, `/chunk`, `/p.gif`, `/config.js`, `/config.json`, `/health`, tracker files) on Node's `http` module. It writes **the same rows to the same SQLite schema** as the Python collector (`data_dir/events.db` and `data_dir/replay.db`), so the Python enrichment jobs, `jobs.py` maintenance commands and the dashboard work on its data unchanged. The shared conformance suite checks it.

No npm dependencies: SQLite comes from Node's built-in `node:sqlite`, gzip from `node:zlib` (decoding exactly as Python's `zlib` does) and `CompressionStream`, HMAC from `node:crypto`.

## Requirements

- Node.js **22.13 or later** (where `node:sqlite` needs no flag; 24 LTS recommended). `node:sqlite` still prints an `ExperimentalWarning`; `npm start` hides it with `--disable-warning=ExperimentalWarning`.
- Python 3.9+ wherever you generate the configuration and run the cron jobs (the same `server/python` package).

## Configuration

The TOML file stays the single source of truth. The Node connector reads its **resolved** form, with every default and per-site layer already applied, so it never re-implements the TOML rules:

```sh
cd server/python
python -m tidesight.jobs --config ~/tidesight/tidesight.toml config-json --out ~/tidesight/data/tidesight.json
```

The JSON contains the deployment secret (used to hash IPs and allowance keys), so it is written with mode 600; keep it out of the web root. Regenerate it after every TOML change, and after updating Tidesight: a file from an older `config-json` lacks newer keys (the connector then uses their defaults, and each site's features as announced in `public`). The running server notices the new file within 5 seconds and reloads it. If the new file is invalid, it keeps the previous configuration and logs an error.

`server.data_dir` comes from the JSON (an absolute path when generated by `config-json`). Pass `--data` to override it.

## Running

```sh
node --disable-warning=ExperimentalWarning server.mjs --port 8080 --config ~/tidesight/data/tidesight.json
# or: TIDESIGHT_CONFIG=~/tidesight/data/tidesight.json npm start -- --port 8080
```

| Option | Default | Meaning |
|---|---|---|
| `--config FILE` | `$TIDESIGHT_CONFIG`, else `./tidesight.json` | The resolved JSON (not the TOML). |
| `--host HOST` | `$HOST`, else `127.0.0.1` | Interface to listen on. Use `0.0.0.0` in a container. |
| `--port PORT` | `$PORT`, else `8080` | |
| `--data DIR` | `server.data_dir` | Data directory override. |
| `--scheme http\|https` | `https` if `server.public_url` starts with `https://`, else `http` | The scheme browsers use. Set `https` behind a TLS-terminating proxy, so the `ts_svid` cookie gets `Secure`. |
| `--base-path /prefix` | none | A mount prefix that the proxy does not strip (`/stats/collect` is then handled as `/collect`). |
| `--max-connections N` | `1000` | Open connections at most; further ones are closed as they arrive. |

The process is single-threaded and writes synchronously. Each request runs one short `BEGIN IMMEDIATE` transaction, so requests never interleave inside a transaction. For more throughput, run several processes (pm2 cluster mode, several systemd instances). Each process has its own SQLite connections and its own spool file, and SQLite's locking coordinates the writers (see "Storage, spool and cron" for how long a request waits for a lock). Files the process creates (databases, spool, the generated secret, the log file) are readable by its owner only (umask 077), as with the Python collector.

### Slow and greedy clients

The server holds out against slow and greedy clients by itself:

- **Timeouts.** A request's headers must arrive within 15 s and the whole request within 30 s (else `408` and the connection closes). A connection with no traffic either way for 30 s is closed, including one that sends requests and never reads the answers. An idle keep-alive connection is closed after 65 s.
- **Pipelining.** At most 4 requests may be in flight on one connection; a client that sends more without reading the responses is disconnected.
- **Request bodies** are read into one buffer per request that grows with the bytes actually received (not with the declared `Content-Length`), and all the bodies being read share 48 MiB. Beyond that, `/collect` and `/chunk` answer `503` with `Retry-After: 10` without reading more, and close the connection.
- **Per client**, at most 32 requests that can carry a body (anything but `GET`, `HEAD` and `OPTIONS`) are in flight at once; more answer `503` with `Retry-After: 10`. The client is the allowances' identity (see "Limits and abuse protection").
- **Connections.** At most `--max-connections` are open. A failure to accept one (out of file descriptors) is logged and the server keeps running.
- **Cheap answers stay cheap.** Tracker files are served from memory (read once, checked against the disk at most every 2 s). `/config.js` and the tracker files never touch the database, and waits for another process's lock on it do not hold up the process (next section).

These limits let the collector face the internet directly, but a reverse proxy in front is still recommended (next section). It terminates TLS, and it buffers request bodies, so slow uploads occupy the proxy instead of this single-threaded process.

### Behind a reverse proxy (recommended)

Let nginx, Apache or Caddy terminate TLS and serve the static tracker files, and proxy the collector:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 2m;
    # proxy_request_buffering is on by default: nginx reads the whole body before passing the request on.
}
```

**Caddy** streams request bodies to the backend unless told otherwise, so a slow upload ties up the collector. Make it buffer them, with a buffer at least as large as `max_chunk_kb` (1 MiB by default):

```caddy
stats.example.com {
    reverse_proxy 127.0.0.1:8080 {
        request_buffers 1MiB
        header_up X-Real-IP {remote_host}
    }
}
```

**Forwarding headers are not trusted at ingest.** `REMOTE_ADDR` (the stored `ip`) is always the socket peer, which behind a proxy is the proxy itself. `X-Forwarded-For`, `X-Real-IP`, `Forwarded` and every other header are stored raw with the request, except the usual secrets (redacted names, Tidesight's own cookies only) and the `Referer`, whose URL secrets are redacted with the site's `redact_params` and `redact_paths` (`core/redact.mjs`, a port of `redact.py`). Enrichment decides which address is the visitor's (`[enrich] ip_header` and `trusted_proxies` in the TOML), and that decision can change later without losing data. Two settings matter behind a proxy:

- `[server] rate_limit_key = "x-real-ip"` with `rate_limit_proxies = ["127.0.0.1/32"]` (the proxy's address). Otherwise every visitor shares the proxy's address, with one set of allowances and one limit of requests in flight (see below). The header is believed only from the listed proxies and only when it holds an IP address. Its last value is used (the one the nearest proxy appended), so use a header the proxy sets itself.
- `--scheme https` (or `server.public_url = "https://…"`): this marks the server cookie `Secure`.

Node's keep-alive timeout is 65 s, so it outlives the usual proxy idle timeouts.

### pm2

```sh
pm2 start server.mjs --name tidesight --node-args="--disable-warning=ExperimentalWarning" -i 2 \
    -- --port 8080 --config /srv/tidesight/tidesight.json
```

### Passenger (Node.js apps)

Passenger replaces the port given to `listen()` with its own socket, so no port is needed. It does not pass command-line options, so set the configuration through the environment. If your Passenger does not load ES-module startup files, use a one-line CommonJS `app.js` containing `import("./server.mjs");`:

```nginx
passenger_app_type node;
passenger_startup_file app.js;            # or server.mjs
passenger_env_var TIDESIGHT_CONFIG /home/me/tidesight/tidesight.json;
```

## Storage, spool and cron

Writes go to `data_dir/events.db` and `data_dir/replay.db`, with the configured `journal_mode` and `synchronous`. Migrations run on first use and are tracked with `PRAGMA user_version`; an `ADD COLUMN` whose column already exists is skipped, as in Python, so a database without a `user_version` (an imported D1 export) migrates cleanly.

**Lock waits.** node:sqlite is synchronous, so SQLite's own wait for another process's write lock (a cron job, another collector process) would freeze every request of this process. The collector therefore takes the write lock without SQLite's busy handler, tries again every 10 ms between turns of the event loop while other requests are served, and gives up after 200 ms, whatever `busy_timeout_ms` says. After such a failure it leaves SQLite alone for 10 s. Inside a transaction, and for reads, SQLite's own wait applies, also capped at 200 ms; with the default WAL journal nothing there waits for another process (with `journal_mode = "delete"`, a commit or a read can).

If SQLite fails (a lock held too long, a disk error, an unreadable file), the request is appended to the **spool** instead: one JSON line per record in `data_dir/spool/<events|chunks>/<YYYY-MM-DD>/<host>-<pid>.jsonl`. This is byte-compatible with the Python collector's spool, so the usual cron job imports it:

```sh
python -m tidesight.jobs --config ~/tidesight/tidesight.toml cron        # loads the spool, then enriches
```

With `storage_mode = "spool"`, every write goes to the spool, and the allowances below are approximate (counted in memory, per process, for the current minute; `/collect` and `/chunk` separately, as with events.db and replay.db), as in Python; the same holds while SQLite fails over to the spool. Refusals are written as summed counter lines, at most once a minute per process and when the server stops. Run the enrichment, backup and other jobs from cron exactly as for the Python collector. They only need the data directory.

Logs go to stderr, or to `server.log_file`, in the Python collector's format. Errors in the request path (storage unavailable, SQLite failing over to the spool, unexpected failures) are logged in full for the first 5 of each minute, then only counted (`N more errors in the previous minute (not logged)`), so a flood of failing requests cannot fill a small disk with log lines. The same throttle covers the warning about a `journal_mode` SQLite would not set, which reconnections would otherwise repeat.

## Limits and abuse protection

The connector applies the limits of [`docs/configuration.md`](../../docs/configuration.md) ("Limits and abuse protection") exactly as the Python collector does, with the same counters and status codes:

- **The client** is the socket peer, or the last value of the `rate_limit_key` header, believed only when the peer is in `rate_limit_proxies` and the value is an IP address (a port is ignored). Only header fields named exactly like `rate_limit_key` count. If one whose name has `_` for `-` comes along (`X_Real_IP` next to `X-Real-IP`), the header is not believed and the socket peer is the client: a proxy sets only its own header, so the other one comes from the client. An IPv6 client is its `rate_limit_ipv6_prefix` network (default /64).
- **Allowances per client and minute**, in the `rate_limits` table, checked in the write transaction in this order: `r:` requests (`rate_limit_per_minute`) and `kb:` kilobytes (`rate_limit_kb_per_minute`); for `/chunk`, in replay.db, `chunk_rate_limit_per_minute` and `chunk_kb_per_minute`. A flagged request also uses `f:` (`flagged_per_minute`) and `*f` (`flagged_global_per_minute`, everyone together). The keys hold the client hashed with the deployment secret (`r:h:3f2a…`, as `hash_ip` writes it), so the table and its backups never hold an address. Over an allowance: `429` with `Retry-After: 60`, except that malformed (`400`) and oversize (`413`) requests keep their status.
- **Early refusal.** A client already over its request or kilobyte allowance this minute is refused (`429`) before its body is decompressed or parsed, the costly part of a request: it is charged and counted as any refusal, under the site the query string names if that site is configured. This comes before the DNT/GPC checks, so a drop beyond the allowance answers `429` too.
- **Kilobytes charged:** on `/collect`, the largest of the bytes received, the bytes after decompression, 256 per stored hit and the stored hits' JSON, plus the query string, the stored headers and the kept cookies (an oversize body counts as `max_payload_kb` + 1 byte); on `/p.gif`, the query string (at least 256) plus headers and cookies; on `/chunk`, the body, the query string and the user-agent, origin and referer kept in `meta`.
- **Flagged** means a site status other than `ok`, an unreadable body, or no or too many events (a pixel only by its site status); a batch with a few invalid events or a bad version is not flagged.
- **Counter-only requests** (DNT/GPC drops, oversize chunks) write their counter only within the client's `r:` allowance.
- **Daily quota per site:** `max_hits_per_day` stored hits per UTC day, off by default (`429` beyond, counted `over_quota`). Stored hits are counted per site and day as `hits`.
- **Chunk kinds** need their feature on for the site (`replay`, `mouse_moves` for `mouse`, `dom_snapshots` for `snapshot`); others are stored flagged (`feature_off`, `site_ok = 0`).
- **Bodies:** at most `max_events_per_request` events become hits (the raw body keeps the whole batch, `400`); JSON nested deeper than 64 levels is unreadable (`bad_json: nested deeper than 64 levels`, `400`), and so is a number beyond a double's range (`bad_json: number out of range`); at most 20 cookies are kept per request.
- **Disk space**: below `min_free_disk_mb` free on the data directory's file system (`fs.statfsSync`, read at most every 10 s), `/collect` and `/chunk` answer `503` with `Retry-After: 300` without storing, and `/p.gif` still answers its GIF. This measures the file system's free space, not a per-user disk quota.

## Tests

From the repository root:

```sh
TIDESIGHT_CONNECTORS=node python -m pytest server/python/tests/test_conformance.py -q
cd server/node && npm test   # unit tests, including the Worker's (see server/worker/README.md)
```

The unit tests cover the spool allowances, the error-log throttle, the URL redaction vectors, the client key header rules, CPython-exact helpers on hostile input (`fnmatch`, `int()`), gzip decoding, migrations, lock waits and the Worker's D1 store.

## Differences from the Python collector

The connector mirrors `collect.py`: the same status codes and headers, and the same rows down to the JSON text of `data`, `envelope` and `headers`. That includes Python's int/float distinction, exact big integers, dict key order, `repr()` of floats, `json` error messages, `parse_qs`, `fnmatch`, gzip decoding (only the first member, zlib's own error texts) and IP anonymisation, which are reimplemented in `core/`. Known differences:

- **HTTP details belong to the server, not the app.** Chunked request bodies are read (`wsgiref` reads none). A request without `Content-Type` is stored without one (`wsgiref` invents `text/plain`). Duplicate headers are joined with `", "` (`"; "` for `Cookie`). Raw non-ASCII bytes in the request line are refused by Node's HTTP parser. The timeouts and per-connection and per-client limits above are the connector's own; Python leaves them to its server.
- **The client key header** is not believed next to a field whose name has `_` for `-` (above). Python's WSGI server merges the two fields into one variable, so Python cannot tell them apart.
- **Lock waits** are at most 200 ms on the request path, then SQLite is left alone for 10 s; Python waits up to `busy_timeout_ms` each time. Meanwhile `/health` relies on the spool alone (`503` without `spool_fallback`), where Python would still read the database.
- **Nesting.** JSON nested deeper than 981 levels is refused with Python's `RecursionError` text; Python's exact limit depends on its version and stack depth.
- **`server` column.** It holds `connector: "node"`, the socket ports and `server_software`.
- **`rate_limits` pruning.** Rows older than an hour are pruned at most once a minute for each database, 20,000 at a time (Python's timer is shared by events.db and replay.db).
