# Tidesight collector for Node.js

The ingest endpoints of [`docs/protocol.md`](../../docs/protocol.md) (`/collect`, `/chunk`, `/p.gif`, `/config.js`, `/config.json`, `/health`, tracker files) on Node's `http` module. It writes **the same rows to the same SQLite schema** as the Python collector (`data_dir/events.db` and `data_dir/replay.db`), so the Python enrichment jobs, `jobs.py` maintenance commands and the dashboard work on its data unchanged. The shared conformance suite checks it.

No npm dependencies: SQLite comes from Node's built-in `node:sqlite`, gzip from `CompressionStream`/`DecompressionStream`, hashing from Web Crypto.

## Requirements

- Node.js **22.13 or later** (where `node:sqlite` needs no flag; 24 LTS recommended). `node:sqlite` still prints an `ExperimentalWarning`; `npm start` hides it with `--disable-warning=ExperimentalWarning`.
- Python 3.9+ wherever you generate the configuration and run the cron jobs (the same `server/python` package).

## Configuration

The TOML file stays the single source of truth. The Node connector reads its **resolved** form, with every default and per-site layer already applied, so it never re-implements the TOML rules:

```sh
cd server/python
python -m tidesight.jobs --config ~/tidesight/tidesight.toml config-json --out ~/tidesight/tidesight.json
```

The JSON contains the deployment secret (used to hash IPs), so it is written with mode 600; keep it out of the web root. Regenerate it after every TOML change. The running server notices the new file within 5 seconds and reloads it. If the new file is invalid, it keeps the previous configuration and logs an error.

`server.data_dir` comes from the JSON (an absolute path when generated by `config-json`). Pass `--data` to override it.

## Running

```sh
node --disable-warning=ExperimentalWarning server.mjs --port 8080 --config ~/tidesight/tidesight.json
# or: TIDESIGHT_CONFIG=~/tidesight/tidesight.json npm start -- --port 8080
```

| Option | Default | Meaning |
|---|---|---|
| `--config FILE` | `$TIDESIGHT_CONFIG`, else `./tidesight.json` | The resolved JSON (not the TOML). |
| `--host HOST` | `$HOST`, else `127.0.0.1` | Interface to listen on. Use `0.0.0.0` in a container. |
| `--port PORT` | `$PORT`, else `8080` | |
| `--data DIR` | `server.data_dir` | Data directory override. |
| `--scheme http\|https` | `https` if `server.public_url` starts with `https://`, else `http` | The scheme browsers use. Set `https` behind a TLS-terminating proxy, so the `ts_svid` cookie gets `Secure`. |
| `--base-path /prefix` | none | A mount prefix that the proxy does not strip (`/stats/collect` is then handled as `/collect`). |

The process is single-threaded and writes synchronously. Each request runs one short `BEGIN IMMEDIATE` transaction, so requests never interleave inside a transaction. For more throughput, run several processes (pm2 cluster mode, several systemd instances). Each process has its own SQLite connections and its own spool file, and SQLite's locking and `busy_timeout_ms` coordinate the writers.

### Behind a reverse proxy (recommended)

Let nginx, Apache or Caddy terminate TLS and serve the static tracker files, and proxy the collector:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 2m;
}
```

**Forwarding headers are not trusted at ingest.** `REMOTE_ADDR` (the stored `ip`) is always the socket peer, which behind a proxy is the proxy itself. `X-Forwarded-For`, `X-Real-IP`, `Forwarded` and every other header are stored raw with the request. Enrichment decides which address is the visitor's (`[enrich] ip_header` and `trusted_proxies` in the TOML), and that decision can change later without losing data. Two settings matter behind a proxy:

- `[server] rate_limit_key = "x-real-ip"`: otherwise every visitor shares the proxy's address and one rate-limit budget. Use a header the proxy sets itself and overwrites. The first `X-Forwarded-For` entry is client-controlled.
- `--scheme https` (or `server.public_url = "https://…"`): this marks the server cookie `Secure`.

Node's keep-alive timeout is 65 s, so it outlives the usual proxy idle timeouts.

### systemd

```ini
# /etc/systemd/system/tidesight.service
[Unit]
Description=Tidesight collector (Node)
After=network.target

[Service]
User=tidesight
Environment=TIDESIGHT_CONFIG=/srv/tidesight/tidesight.json
ExecStart=/usr/bin/node --disable-warning=ExperimentalWarning /srv/tidesight/server/node/server.mjs --port 8080 --scheme https
Restart=on-failure
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

### pm2

```sh
pm2 start server.mjs --name tidesight --node-args="--disable-warning=ExperimentalWarning" -i 2 \
    -- --port 8080 --config /srv/tidesight/tidesight.json
```

### Passenger (Node.js apps)

Passenger replaces the port given to `listen()` with its own socket, so no port is needed. It does not pass command-line options, so set the configuration through the environment. If your Passenger does not load ES-module startup files, use a one-line CommonJS `app.js` containing `import("./server.mjs");`:

```nginx
passenger_app_type node;
passenger_startup_file app.js;            # or server.mjs
passenger_env_var TIDESIGHT_CONFIG /home/me/tidesight/tidesight.json;
```

## Storage, spool and cron

Writes go to `data_dir/events.db` and `data_dir/replay.db`, with the configured `journal_mode`, `synchronous` and `busy_timeout_ms`. Migrations run on first use and are tracked with `PRAGMA user_version`.

If SQLite fails (locked beyond the timeout, disk error, unreadable file), the request is appended to the **spool** instead: one JSON line per record in `data_dir/spool/<events|chunks>/<YYYY-MM-DD>/<host>-<pid>.jsonl`. This is byte-compatible with the Python collector's spool, so the usual cron job imports it:

```sh
python -m tidesight.jobs --config ~/tidesight/tidesight.toml cron        # loads the spool, then enriches
```

With `storage_mode = "spool"`, every write goes to the spool. Rate limiting is then approximate (in memory, per process), as in Python. Run the enrichment, backup and other jobs from cron exactly as for the Python collector. They only need the data directory.

Logs go to stderr, or to `server.log_file`, in the Python collector's format.

## Differences from the Python collector

The connector mirrors `collect.py`: the same status codes and headers, and the same rows down to the JSON text of `data`, `envelope` and `headers`. That includes Python's int/float distinction, exact big integers, dict key order, `repr()` of floats, `json` error messages, `parse_qs`, `fnmatch` and IP anonymisation, which are reimplemented in `core/`. Known differences:

- **Gzip edge cases.** Trailing bytes after the gzip member, or several concatenated members, are flagged `bad_gzip` here; Python decodes the first member and ignores the rest. Errors inside the deflate data read `Error -3 while decompressing data: invalid compressed data` instead of zlib's specific text. Header errors and `truncated gzip data` match.
- **HTTP details belong to the server, not the app.** Chunked request bodies are read (`wsgiref` reads none). A request without `Content-Type` is stored without one (`wsgiref` invents `text/plain`). Duplicate headers are joined with `", "` (`"; "` for `Cookie`). Raw non-ASCII bytes in the request line are refused by Node's HTTP parser.
- **Nesting.** JSON nested deeper than 981 levels is refused with Python's `RecursionError` text; Python's exact limit depends on its version and stack depth.
- **`server` column.** It holds `connector: "node"`, the socket ports and `server_software`.
